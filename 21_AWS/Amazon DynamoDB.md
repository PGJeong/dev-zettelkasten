- DynamoDB는 온라인 트랜잭션 처리(OLTP) 워크로드용으로 설계된 **서버리스, 완전관리형NoSQL** 데이터베이스 서비스

![[../80_Assets/Pasted image 20260803100853.png]]

- 유연한 스키마
- **JSON 문서** 또는 **키-값** 데이터 구조를 모두 지원
- 이벤트 중심 프로그래밍 지원

# 작동 방식

![[../80_Assets/Pasted image 20260803135433.png]]

- 데이터는 테이블에 저장, 테이블에는 속성으로 이루어진 항목이 있음
- **항목**은 RDB의 행, **속성**은 열로 간주할 수 있음

### 기본 키의 두 가지 유형

- **파티션 키** - 데이터가 어떤 물리적 공간(파티션)에 저장될지 결정하는 기준
  ![[../80_Assets/Pasted image 20260803142012.png]]
	- 파티션 키 값을 내부 해시 함수에 입력하여 데이터의 물리적 저장 위치를 결정

- **파티션 키+정렬 키 조합** - 정렬 키는 동일한 파티션 키 내에서 데이터를 정렬하고 구별
  ![[../80_Assets/Pasted image 20260803142036.png]]
	- 파티션 키가 같은 데이터들은 정렬 키 값을 기준으로 오름차순 정렬되어 같은 물리 공간에 모여 저장
	- 파티션 키와 달리 일치(`=`) 검색뿐만 아니라, 범위 및 크기 비교 연산을 모두 지원

### 키-값 구조

![[../80_Assets/Pasted image 20260803140131.png]]

- 고유한 키(Key) 하나를 던지면 값(Value)이 나옴
- 전통적인 형태의 단순한 구조로, 기본 키에 대응하는 값이 하나의 단순한 데이터(문자열, 숫자 등)인 경우

### JSON 문서 구조

![[../80_Assets/Pasted image 20260803140150.png]]

- 하나의 키 아래에 복잡하게 얽힌 JSON 객체가 통째로 들어감
- DynamoDB는 내부적으로 `Map`(JSON 객체)과 `List`(배열)라는 복합 데이터 타입을 지원하므로, 중첩된 JSON 문서를 그대로 저장할 수 있음 (최대 32수준의 깊이까지 중첩)

### 일관성

- DynamoDB는 데이터를 읽을 때 **두 가지 수준의 데이터 일관성(Consistency)** 모델이 있음

- **최종적 일관성 (Eventually Consistent Reads)**
	- DynamoDB의 기본(Default) 읽기 방식
	- 데이터를 쓰거나 수정하면, 전 세계 여러 복제본 서버로 데이터가 퍼지는 데 약간의 시간이 걸림. 최종적 일관성은 복제가 완료되기 전에 읽기 요청을 처리할 수 있음
	- 직전에 변경한 데이터가 즉시 반영되지 않은 **과거의 데이터가 조회될 가능성**이 있음
	- 처리 속도가 가장 빠르고, 읽기 비용(RCU)이 강력한 일관성에 비해 절반 수준으로 저렴

- **강력한 일관성 (Strongly Consistent Reads)**
	- **항상 가장 최신의 데이터를 보장**해야 할 때 사용하는 옵션
	- 데이터를 읽기 전에 모든 복제본 중에서 **가장 최신 업데이트가 완료된 서버를 찾아** 데이터를 가져옴
	- 직전에 쓰거나 수정한 데이터가 **100% 즉시 반영된 최신 데이터**임을 보장
	- 네트워크 지연이 발생할 수 있어 속도가 최종적 일관성보다 미세하게 느릴 수 있으며, 읽기 비용(RCU)이 **2배로 소모**

| 구분              | 최종적 일관성 (Eventual)       | 강력한 일관성 (Strong)                   |
| --------------- | ------------------------ | ---------------------------------- |
| **기본 설정 여부**    | 기본값 (Default)            | 요청 시 명시 필요 (`ConsistentRead=true`) |
| **최신 데이터 보장**   | 보장 안 됨 (과거 데이터 가능성 존재)   | 100% 보장 (무조건 최신 데이터)               |
| **비용 (RCU 소모)** | **0.5 RCU** (최대 4KB당)    | **1 RCU** (최대 4KB당)                |
| **추천 사용 사례**    | 블로그 댓글, 좋아요 수, 소셜 미디어 피드 | 금융 잔액, 티켓 예매, 실시간 재고 확인            |

### 읽기 및 쓰기 용량 단위

- 테이블을 생성할 때 읽기 및 쓰기 처리량 값을 지정해야함
- **읽기 용량 단위(RCU)** - 최대 4KB 항목의 초당 강력하게 일관된 읽기 수
- **쓰기 용량 단위(WCU)** - 초당 1KB의 쓰기 수

### API 작업 종류

- **쓰기**
	- `PutItem` - 지정된 기본 키에 항목을 쓰기
	- `UpdateItem` - 지정된 기본 키를 사용하여 항목의 속성을 변경
	- `BatchWriteItem` - 지정된 기본 키에 항목 묶음을 쓰기
	- `deleteItem` - 지정된 기본 키와 연결된 항목을 제거
- **읽기**
	- `GetItem` - 지정된 기본 키와 연결된 항목을 검색
	- `BatchGetItem` - 지정된 기본 키의 이 묶음으로 항목을 검색
	- `Query` - 지정된 파티션 키의 경우 정렬 키 표현식(정순/역순)과 일치하는 항목을 검색
	- `Scan` - 테이블에 있는 모든 항목을 검색

### 보조 인덱스

- 테이블의 기본 키에 속하지 않은 속성에 대해 쿼리를 수행하려면 보조 인덱스를 생성하면 됨
- **로컬**과 **글로벌** 두 가지 유형이 있음
- 테이블당 최대 5개의 글로벌 보조 인덱스와 5개의 로컬 보조 인덱스를 정의할 수 있음

- **글로벌 보조 인덱스 (GSI, Global Secondary Index)**
  ![[../80_Assets/Pasted image 20260803145251.png]]
	- 기본 테이블과 **완전히 독립된 새로운 파티션 키와 정렬 키**를 구성하여 데이터를 조회하는 인덱스 (가장 보편적으로 사용)
	- 테이블을 새로 하나 더 만드는 것과 비슷. 기본 테이블의 파티션 키가 무엇이든 상관없이, 내가 원하는 완전히 새로운 속성을 파티션 키로 지정할 수 있음
	- **최종적 일관성(Eventually Consistent)**만 지원
	- 테이블을 만든 후에도 언제든지 자유롭게 추가하거나 삭제할 수 있음

- **로컬 보조 인덱스 (LSI, Local Secondary Index)**
  ![[../80_Assets/Pasted image 20260803145214.png]]
	- 기본 테이블의 **파티션 키는 그대로 공유**하면서, **정렬 키만 다른 속성으로 바꾸어** 조회하는 인덱스
	- 로컬(Local)이라는 이름처럼, 동일한 파티션 안에서만 작동. 파티션 키는 무조건 원래 테이블과 같아야 하고, 정렬 키만 변경
	- 기본 테이블의 파티션을 공유하므로 **강력한 일관성(Strongly Consistent)**을 지원
	- 무조건 **테이블을 처음 만들 때만** 같이 만들 수 있음. 나중에 추가 또는 삭제 불가능

| 항목             | 글로벌 보조 인덱스 (GSI)     | 로컬 보조 인덱스 (LSI)          |
| -------------- | -------------------- | ------------------------ |
| **파티션 키 변경**   | **가능** (완전히 다른 키 지정) | **불가능** (원래 테이블 키 강제 사용) |
| **정렬 키 변경**    | **가능**               | **가능**                   |
| **생성/삭제 타이밍**  | 언제든지 생성 및 삭제 가능      | 테이블 생성 시에만 가능 (삭제 불가)    |
| **데이터 읽기 일관성** | 최종 일관성만 가능           | 최종/강력한 일관성 둘 다 가능        |
| **데이터 용량 제한**  | 제한 없음                | 동일 파티션 내 최대 10GB 제한      |

### DynamoDB 스트림

![[../80_Assets/Pasted image 20260803145710.png]]

- 테이블의 데이터가 변경(추가, 수정, 삭제)되는 순간, 그 변경 이력을 실시간으로 감지하고 기록하는 타임라인 기능
- 이 기능을 켜두면 데이터베이스에 변화가 생겼을 때 다른 시스템(예: AWS Lambda)을 깨워 후속 작업을 자동으로 처리할 수 있음
- 스트림 레코드는 24시간 동안 사용 가능

# 운영

- **DynamoDB Auto Scaling** - 테이블의 트래픽 변화에 맞춰 **처리량(RCU/WCU)을 자동으로 조절**하는 기능 (기본적으로 활성화 됨)
- **Global Tables** - 전 세계 여러 AWS 리전(Region)에 **실시간으로 동기화되는 완전 분산 테이블**을 구동하는 기능
- **IAM 액세스 제어** - DynamoDB는 IAM과 긴밀하게 통합되어 있어 API 단위 권한 관리가 가능
- **Amazon DynamoDB Accelerator(DAX)** - DynamoDB 앞에 붙여서 사용하는 인메모리 캐시(In-memory Cache) 서비스
- **백업 및 복원** - DynamoDB는 온디맨드 백업 및 복원 기능을 제공 (사용자가 원하는 시점에 버튼 하나로 몇 초 만에 테이블 전체를 백업하는 기능)

# 설계 고려 사항

- **균일한 워크로드**
  ![[../80_Assets/Pasted image 20260803170654.png]]
	- 파티션 키 기반의 데이터 분산은 핫 파티션을 방지하고 처리량을 극대화하는 데 필수적
	- 이를 위해 고유성이 높은 파티션 키를 선정하고, 데이터 저장 시 임의의 값을 결합하여 트래픽을 여러 파티션에 균등하게 분산시키는 '쓰기 샤딩(Write Sharding)' 기법이 권장

- **핫 데이터와 콜드 데이터**
  ![[../80_Assets/Pasted image 20260803170802.png]]
	- 시계열 데이터의 액세스 빈도에 따라 최신 '핫' 데이터와 과거 '콜드' 데이터를 서로 다른 테이블로 분리하여 성능과 비용을 최적화
	- 오래된 데이터는 Amazon S3와 같은 저비용 저장소로 이관하고 DynamoDB 테이블에서 삭제하여 스토리지 비용을 절감

- **큰 속성 관리**
  ![[../80_Assets/Pasted image 20260803170919.png]]
	- DynamoDB는 **항목 크기에 제한(최대 400KB)**이 있으므로, 데이터 크기를 작게 유지하기 위해 다음과 같은 세 가지 방법을 활용할 수 있음
	- **Amazon S3 활용** - 용량이 큰 속성 값은 비용이 저렴한 **S3 버킷에 별도로 저장**하고, DynamoDB에는 해당 S3 파일의 주소(URL 또는 경로)만 기록
	- **데이터 압축** - 대용량 텍스트나 바이너리 데이터를 DynamoDB에 저장하기 전에 **애플리케이션 단에서 압축**하여 크기를 줄인 후 저장
	- **항목 분할** - 하나의 큰 속성을 여러 개로 쪼개어 **동일한 파티션 키 아래의 여러 항목(정렬 키 활용)**으로 분산하여 저장

- **버전 번호를 이용한 낙관적 잠금**
	- 여러 사용자가 동시에 같은 데이터를 수정할 때 데이터가 꼬이는 것을 막는 설계 패턴
	- 데이터가 자주 변경되지 않을 것이라 '낙관적'으로 가정하고, 조건부 표현식과 버전 번호를 활용해 충돌을 방지
	
	1. **조회**: 데이터를 읽으면서 현재의 버전 번호(예: `versionNum = 0`)를 기억
	2. **수정 및 버전 증가**: 비즈니스 로직을 처리한 뒤, 메모리에서 버전 번호를 1 증가(`versionNum = 1`)
	3. **조건부 쓰기**: 테이블에 저장할 때, **"현재 저장된 버전 번호가 내가 처음에 읽었던 0과 같을 때만 수정을 허용한다"**는 조건부 표현식(Conditional Expression)을 걸고 업데이트를 시도
	4. **재시도**: 만약 그 사이 다른 요청이 먼저 데이터를 바꿔서 버전 번호가 달라졌다면 쓰기는 실패하며, 다시 **1단계(처음부터 읽기)**로 돌아가 작업을 재시도

- **자주 액세스하는 작은 속성을 별도 테이블에 저장**
  ![[../80_Assets/Pasted image 20260803173803.png]]
	- 테이블의 전체 항목 크기는 크지만 특정 속성만 자주 조회·변경된다면, 대용량 속성과 분리하여 별도 테이블로 구성함으로써 처리량과 비용을 최적화할 수 있음
