- 서버리스 컴퓨팅을 사용하면 서버를 생각하지 않고 애플리케이션과 서비스를 구축하고 실행할 수 있음
	- 프로비저닝하거나 관리할 인프라가 없음
	- 서버를 프로비저닝, 운영 또는 패치할 필요가 없음
	- 서버 단위가 아니라 소비 단위별로 오토 스케일링
	- 종량제(On-demand) 결제 모델
	- 가용성 및 내결함성 기본 제공

- 이벤트 기반 아키텍처를 사용하면 서비스를 분리하여 작업 속도를 높이고 애플리케이션을 더 쉽게 디버그할 수 있음
- 서비스 간 통신은 동기식이거나 비동기식일 수 있음
	- **비동기식 통신**의 경우, 이벤트 기반 아키텍처에는 응답 경로가 없음. 서비스가 이벤트를 표시한 후, 즉시 다음으로 진행
	- **동기식 통신**에서, 클라이언트는 서비스 A에 요청을 보내고, 서비스 A가 서비스 B를 호출하면, 서비스 A는 서비스 B가 응답할 때까지 기다렸다가 최종적으로 클라이언트에 응답

# Amazon EventBridge

- 서버리스 애플리케이션을 지원하는 서비스
- 이벤트를 통해 애플리케이션 구성 요소를 서로 연결하여 확장 가능한 이벤트 기반 애플리케이션을 더 쉽게 구축할 수 있도록 함

- EventBridge 워크플로에는 이벤트, 대상, 규칙이라는 3가지 구성 요소가 있음
	- **이벤트** - AWS 환경, 애플리케이션, 서비스와 같은 환경의 변동을 나타냄
	- **타깃** - 이벤트가 규칙에 정의된 이벤트 패턴과 일치할 때, EventBridge가 이벤트를 보내는 리소스 또는 엔드포인트
	- **규칙** - 들어오는 이벤트 중 일치하는 것을 찾아서 대상으로 보내서 처리하는 규칙

### 작동 방식

1. **이벤트 소스에서 수신한 이벤트**
   ![[../80_Assets/Pasted image 20260726230503.png]]
	- EventBridge에 수신되는 모든 이벤트는 이벤트 버스와 연결됨
	- 규칙은 단일 이벤트 버스에 연결되므로, 해당 이벤트 버스의 이벤트에만 적용할 수 있음
	- AWS 서비스로부터 이벤트를 수신하는 기본 이벤트 버스가 있으며, 사용자 지정 이벤트 버스를 생성하여 다른 계정 또는 리전에서 이벤트를 보내거나 받을 수 있음

2. **이벤트 정의**
   ![[../80_Assets/Pasted image 20260726230638.png]]
	- 이벤트에는 항상 유형, 소스 및 이벤트에 대한 세부 정보가 포함되며, 각 구성 요소를 기준으로 필터를 생성할 수 있음
	- 위 예제에서 첫 번째 규칙은 소스 필드에서 일치하는 항목을 찾는 것이고, 두 번째 규칙은 이벤트의 세부 정보 섹션에서 특정 요소를 찾는 것 (둘 다 규칙과 일치함)

3. **대상에 전달된 이벤트**
   ![[../80_Assets/Pasted image 20260726230838.png]]
	- 다수의 대상을 각 규칙에 연결할 수 있음 (규칙마다 최대 5개의 대상을 정의할 수 있음)
	- 이벤트 데이터를 대상에 전달하려면 EventBridge는 대상 리소스에 액세스할 수 있는 권한이 필요

### 스키마 레지스트리

- **스키마**는 이벤트의 구조를 나타내며, 이벤트에 포함된 각 데이터의 제목 및 형식 등과 같은 정보 (e.g. 이름 및 전화번호 같은 필드, 이름이 텍스트 문자열이고 전화번호가 정수)
- 스키마에는 전화번호 길이가 10자리여야 한다 같은 패턴에 대한 정보도 포함될 수 있음

- **스키마 레지스트리**는 이벤트 버스로 전송되는 이벤트의 데이터 구조(스키마)를 한곳에 모아 관리하고 공유하는 중앙 저장소
- 이벤트 기반 아키텍처에서 각 마이크로서비스가 주고받는 이벤트의 형태를 명확하게 정의하고 추적할 수 있도록 도움
- 레지스트리에 스키마를 수동으로 추가하거나 EventBridge **스키마 검색 기능**을 켜서 이 프로세스를 자동화할 수 있음

# AWS Lambda

- AWS Lambda는 서버를 프로비저닝하거나 관리하지 않고도 애플리케이션 또는 백엔드 코드를 실행할 수 있게 하는 이벤트 중심의 서버리스 컴퓨팅 서비스
- Lambda는 스스로 실행되지 않고 특정 **이벤트(Trigger)**가 발생해야 작동함

- **실행 시간 제한** - 하나의 함수는 **최대 15분**까지만 실행될 수 있어 대규모 장시간 데이터 연산에는 부적합
- **콜드 스타트(Cold Start)** - 함수가 오랫동안 호출되지 않았다가 처음 실행될 때, 컨테이너 환경을 새로 만드느라 약간의 지연 시간(수백 ms~수 초)이 발생
- **상태 비저장(Stateless)** - 각 함수는 실행된 후 완전히 독립적으로 소멸하므로, 로컬 서버에 데이터를 저장해 두고 다음 호출 때 이어서 쓸 수 없음

- Lambda를 사용하면 사실상 모든 유형의 애플리케이션 또는 백엔드 코드를 실행할 수 있음 (Lambda가 지원하는 언어 중 하나로 코드를 작성하면 됨)
- Lambda는 필요할 때만 함수를 실행하고 하루에 몇 개의 요청에서 초당 수천 개의 요청까지 자동으로 규모를 조정
- 사용한 컴퓨팅 시간에 대해서만 비용을 지불하면 되므로 코드가 실행되지 않을 때는 비용이 청구되지 않음

- 이벤트는 Lambda 함수가 처리할 데이터가 포함된 JSON 형식의 문서로, 런타임은 이벤트를 객체로 변환하여 함수 코드에 전달함 (개발자가 직접 이벤트의 구조와 콘텐츠를 결정)

# Amazon API Gateway

- **Amazon API Gateway**는 규모와 상관없이 API의 생성, 게시, 유지 관리, 모니터링, 보안을 용이하게 해주는 서비스

- API Gateway는 AWS Lambda와 긴밀하게 통합되며, 동기식 호출에서 Lambda 서비스는 이벤트를 함수에 직접 전송한 다음, 호출자에게 응답을 다시 전송
  ![[../80_Assets/Pasted image 20260727024339.png]]
	- API Gateway는 Lambda 함수를 동기식으로 호출하며 기본 제공되는 제한 시간은 30초
	- Lambda 서비스가 30초 내에 함수를 성공적으로 간접 호출하지 못하거나, 함수가 실행되지만 오류가 발생할 경우 API와 호출 클라이언트에 해당 오류가 반환
	- 재시도 기능이 기본 제공되지 않으며, 요청 이벤트는 응답을 기다려야 함

### API Gateway 기능

- **개발자 기능**
	- RESTful(REST/HTTP) 또는 WebSocket API 생성
	- 여러 버전의 API 호스팅
	- API에서 SDK 생성
	- Swagger 또는 OpenAPI 3.0 정의 가져오기 및 내보내기
	- 다른 AWS 서비스 및 백엔드와 통합
	- 프록시 또는 사용자 지정 통합 생성

- **보안 및 규모 조정 기능**
	- 자체적인 서명 버전 4 인증을 작성하지 않고도 Lambda 간접 호출
	- 예상되는 액세스 패턴과 가장 잘 맞는 엔드포인트 유형 선택
	- **API에 대한 액세스 권한 부여**
	- 요청 스로틀
	- 카나리 배포 수행
	- AWS 웹 애플리케이션 방화벽(AWS WAF)과 통합

### 아키텍처 예시

![[../80_Assets/Pasted image 20260727024631.png]]
- 클라이언트 브라우저가 Amazon S3에서 호스팅된 정적 웹 페이지를 요청
- 클라이언트 브라우저는 이 웹 페이지를 사용하여 REST API를 통해 API Gateway와 통신
- API Gateway는 요청을 인증하고 권한을 부여하며, DynamoDB와 통신하는 Lambda 함수를 간접적으로 호출
- 반복 요청을 처리할 때 지연 시간과 백엔드 로드를 줄이기 위해, API Gateway 캐시가 포함
- API Gateway는 Amazon CloudWatch로도 로그를 전송

# Amazon SQS (Simple Queue Service)

- **Amazon SQS**는 분산 소프트웨어 시스템 및 마이크로서비스 간에 메시지를 안정적으로 전송, 저장, 수신할 수 있게 지원하는 **완전관리형 메시지 대기열(Message Queue)** 서비스

- **느슨한 결합** - 전처리 단계를 컴퓨팅 단계 및 후처리 단계와 분리할 수 있음. 비동기식 처리를 사용하면 생산자 로직이 소비자 로직과 별개인 자체 구성 요소로 분리
- **스파이크 흡수** - 시스템의 탄력성을 높여줌. 대기열은 급증하는 트래픽 처리를 위한 버퍼로 사용되며, 애플리케이션이 스케일 아웃 작업을 할 수 있는 시간을 벌어줌
- **내결함성** - 애플리케이션 예외나 트랜잭션 장애가 발생하는 경우 처리를 재시도할 수 있음. 최대 재시도 횟수에 도달하면 Amazon SQS는 나중에 다시 처리하거나 디버깅할 수 있는 SQS 배달 못한 편지 대기열로 메시지를 리디렉션할 수 있음

### SQS 대기열

1. **Standard(표준 대기열)**
   ![[../80_Assets/Pasted image 20260727151448.png]]
	- 메시지는 일반적으로 수신된 순서와 동일한 순서로 전송
	- 그러나 고도로 분산된 아키텍처의 특성상 때로는 **2개 이상의 메시지 사본**이 **순서가 맞지 않게** 전송될 수 있음
	- 표준 대기열은 처리할 수 있는 초당 API 직접 호출 수에 거의 제한이 없음

2. **FIFO(FIFO 대기열)**
   ![[../80_Assets/Pasted image 20260727151504.png]]
	- 작업 및 이벤트 **순서가 중요**하거나 **중복 항목이 허용되지 않는 경우**에 적합
	- 정확히 한 번 처리를 제공하지만 초당 API 직접 호출 수가 제한

### 대기열 구성 최적화

- **가시성 제한 시간**
	- 소비자가 수신한 SQS 메시지는 소비자가 삭제할 때까지 대기열에 유지됨
	- 해당 메시지가 일정 기간 동안 다른 소비자에게는 표시되지 않도록 SQS 대기열의 가시성 시간제한 설정을 구성할 수 있음 (다른 소비자가 같은 메시지를 처리하지 못하도록)
	- 가시성 제한 시간이 만료되기 전에 소비자가 메시지를 삭제하지 않을 경우, 다른 소비자가 메시지를 볼 수 있게 되며 해당 메시지는 중복 처리될 수 있음
	- 그러므로 대기열에서 메시지를 처리하고 삭제하는 데 걸리는 최대 시간으로 설정해야

- **폴링 유형**
	- 짧은 폴링이나 긴 폴링을 사용하도록 SQS 대기열을 구성할 수 있음
	- **짧은 폴링(Short Polling)** - 메시지 유무와 관계없이 **즉시 응답** 반환 (메시지가 없으면 빈 응답을 바로 받음)
	- **긴 폴링 (Long Polling)** - 메시지가 올 때까지 **최대 20초간 대기** 후 응답 (대기 중 메시지가 오면 즉시 수신, 끝까지 없으면 타임아웃)

# Amazon SNS (Simple Notification Service)

- 마이크로서비스, 분산 시스템 및 서버리스 애플리케이션 간에 이벤트를 조율하고 알림을 대량으로 발송할 수 있는 **완전관리형 게시/구독(Pub/Sub) 메시징 서비스**

### Pub/Sub 모델

![[../80_Assets/Pasted image 20260727162342.png]]

- **게시자(Publisher)**: 이벤트를 생성하고 SNS **주제(Topic)**로 메시지를 보냄
- **주제(Topic)**: 메시지가 모이는 방송 채널
- **구독자(Subscriber)**: 해당 채널을 구독하여 메시지를 실시간으로 받아보는 주체

### Amazon SNS의 특성

- 메시지가 성공적으로 전송되면 해당 메시지 회수 불가
- Amazon SNS 전송 정책을 사용해 재시도 패턴(선형, 기하학, 지수 백오프, 최대 및 최소 재시도 지연 및 기타 패턴)을 제어할 수 있음
- Amazon SNS는 가장 크고 수요가 가장 많은 애플리케이션의 요구 사항에 부합하도록 설계되어, 애플리케이션이 무제한의 메시지를 게시할 수 있음

### 팬아웃(Fan-out) 패턴

![[../80_Assets/Pasted image 20260724134324.png]]

- 팬아웃 시나리오에서는 메시지가 SNS 주제로 전송된 후 복제되어 여러 SQS 대기열, HTTP 엔드포인트 또는 이메일 주소로 푸시 (비동기식 병렬 처리가 허용)
- 이 예에서 Amazon SNS는 서로 다른 2개의 SQS 대기열로 주문을 팬아웃
- 2개 Amazon EC2 인스턴스가 각각 대기열을 관찰, 2개의 인스턴스 중 1개는 주문 처리 또는 이행 과정을 진행하고, 다른 1개는 데이터 웨어하우스에 연결되어 접수되는 모든 주문을 분석

### Amazon SNS와 Amazon SQS 비교

| 특성        | Amazon SNS | Amazon SQS |
| :-------- | :--------- | :--------- |
| 메시지 지속성   | 아니요        | 예          |
| 전송 메커니즘   | 푸시(수동적)    | 폴링(능동적)    |
| 생산자 및 소비자 | 게시자 및 구독자  | 발송 또는 수신   |
| 배포 모델     | 일대다        | 일대일        |

# Amazon Cognito

- **Amazon Cognito**는 웹 및 모바일 앱에 회원가입, 로그인, 접근 제어(인증 및 인가) 기능을 쉽고 빠르게 구현할 수 있게 해주는 사용자 관리 서비스
- 회원가입 화면, 비밀번호 찾기, OAuth 로그인(구글 등 서드 파티) 같은 **로그인 관련 복잡한 인프라를 AWS가 대신 구축·관리해 주는 서비스**

### 핵심 구성 요소

- **사용자 풀 (User Pools)** - 인증 (Authentication)
	- "이 사람이 우리 회원이 맞는가?"를 확인하는 회원 정보 저장소
	- 회원가입, 로그인, 비밀번호 변경/재설정 기능 제공
	- **MFA(다요소 인증)** 및 소셜 로그인(구글, 애플, 페이스북, SAML 등) 지원
	- 로그인 성공 시 **JWT(JSON Web Token)** 토큰 발급

- **자격 증명 풀 (Identity Pools)** - 인가 (Authorization)
	- "이 사용자가 어떤 AWS 자원(S3, DynamoDB 등)에 접근할 수 있는가?"를 결정
	- 로그인한 사용자에게 **임시 AWS 자격 증명(IAM Role)**을 부여

### JWT 토큰

- Amazon Cognito(User Pool)에 로그인하면 사용자 인증 및 권한 관리를 위해 JWT(JSON Web Token) 표준 규격의 토큰 3가지를 발급함

1. **ID 토큰 (ID Token)**
	- 로그인한 **사용자의 신원 정보(프로필)**가 담긴 토큰
	- 유저 ID(`sub`), 이름, 이메일, 닉네임, 프로필 사진 주소 등 포함

2. **액세스 토큰 (Access Token)**
	- 사용자가 **특정 기능이나 API를 사용할 권한이 있는지** 확인하는 토큰
	- 사용자가 속한 그룹(Admin, User 등), 허용된 권한 범위(scope), 토큰 발급 및 만료 시간 등 포함

3. **리프레시 토큰 (Refresh Token)**
	- ID 토큰과 액세스 토큰이 만료되었을 때, **로그인을 다시 하지 않고 두 토큰을 새것으로 재발급**받기 위해 사용하는 비밀번호성 토큰
	- 다른 토큰들과 달리 내부 정보를 담은 JWT 형태가 아니라 임의의 문자열 형태이며, **오직 Cognito 서버로 새 토큰을 요청할 때만** 전송

### 사용자 풀을 사용한 권한 부여 흐름

- **사용자 풀 기반(JWT)** - 앱이 **일반 토큰**을 내면 **Lambda 서버의 권한을 빌려** 안전하게 데이터를 대리 처리하는 방식

1. 우선 클라이언트는 사용자 풀을 사용하여 인증
2. 클라이언트는 그 대가로 JWT 3개를 받음
3. 클라이언트가 헤더 안의 자격 증명(ID) 및 액세스 토큰을 API Gateway에 전달
4. API Gateway가 토큰을 검증
5. API Gateway는 백엔드에서 통합되는 리소스를 간접적으로 호출
6. Lambda 함수는 다른 AWS 리소스에 액세스

### 연동 자격 증명을 사용한 IAM 권한 부여

- **연동 자격 증명 기반(IAM)** - 앱이 **임시 AWS 열쇠**를 받아 **유저 개인의 IAM 권한으로 S3/DB에 직접 접근**하여 서버 비용을 없애는 방식

| 구분               | 사용자 풀 기반 (JWT)             | 연동 자격 증명 기반 (IAM)              |
| ---------------- | -------------------------- | ------------------------------ |
| **클라이언트가 쥐는 것**  | 일반 웹 토큰 (**JWT**)          | AWS 전용 **임시 열쇠 세트**            |
| **인증을 검사하는 곳**   | API Gateway가 자체적으로 검증      | AWS IAM 서비스가 암호학적 서명(SigV4) 검증 |
| **DB 접근 권한의 주체** | **Lambda 함수**가 가진 권한을 빌려 씀 | **로그인한 사용자 개인**에게 직접 권한이 귀속됨   |

1. 클라이언트가 Amazon Cognito 사용자 풀을 사용하여 인증
2. 클라이언트가 Amazon Cognito 사용자 풀에서 JWT를 가져옴
3. 클라이언트가 이러한 토큰을 사용하여 임시 AWS 자격 증명을 요청
4. Amazon Cognito 연동 자격 증명이 자격 증명 토큰을 검증
5. Amazon Cognito 연동 자격 증명이 임시 자격 증명을 반환
6. 클라이언트가 이러한 자격 증명을 사용하여 페이로드에 서명
7. 클라이언트가 서명된 페이로드를 사용하여 API를 직접 호출
8. API Gateway가 임시 보안 인증과 연결된 IAM 정책을 확인하고 해당 정책을 제공하는 액션을 허용
9. API Gateway가 IAM 정책에 제공된 권한에 따라 Lambda 함수를 간접적으로 호출
